## 1. Scope

AutoProjectBook automates the creation of the mandatory **Sefer Proyekt (ספר פרויקט)** for Israeli high-school students in the Software Engineering major (5 units) completing MoE questionnaire **883589**.

**In Scope:**
- Web application (SPA) running entirely in the browser
- Support for C#/ASP.NET Core/Blazor capstone projects
- Database support: MS Access (`.mdb`/`.accdb`) and SQL Server T-SQL scripts (`.sql`)
- AI-powered text generation via Google Gemini API
- Auto-generation of UML class diagrams and ERD via Mermaid.js
- Bilingual output: **Hebrew** and **Arabic** (RTL)
- Export to `.docx` format

**Out of Scope (v1.0):**
- PDF export
- Backend / server-side processing
- Projects in Java, Python, or other languages
- Mobile native app
- Cloud storage or collaboration

### FR-01 Onboarding & Configuration

**Priority:** Must Have  
**Epic:** Epic 1 — Onboarding

#### FR-01.1 — Welcome Screen
- The system MUST display a welcome/intro screen explaining what the tool does and what inputs are needed.
- The screen MUST be in the configured language (default: Hebrew).

#### FR-01.2 — Language Selection
- The user MUST be able to select the document output language: **Hebrew (עברית)** or **Arabic (عربية)**.
- The selection MUST change the UI locale and the generated document language simultaneously.
- Default: Hebrew.

#### FR-01.3 — School Metadata Entry
The user MUST be prompted to enter:

| Field | Type | Required | Notes |
|-------|------|----------|-------|
| Student full name | Text | Yes | Displayed on cover page |
| Student ID (ת.ז.) | Text (9 digits) | Yes | Strictly 9 numeric chars |
| School name | Text | Yes | |
| School logo | Image upload | No | PNG/JPG, shown on cover |
| Advisor/teacher name | Text | Yes | |
| Submission date | Date picker | Yes | Defaults to today |
| Class/grade | Text | No | e.g., "י"ב מגמת הנדסת תוכנה" |

#### FR-01.4 — Project Type Selection
The user MUST select their project track to guide AI analysis:

- Blazor / ASP.NET Core Web App
- Windows Application (WPF / WinForms)
- Android Application
- Other (manual description)

#### FR-01.5 — Gemini API Key Entry
- The user MUST enter their Gemini API key to enable AI content generation.
- The key MUST be stored **only** in `sessionStorage` by default.
- Optional: Allow user to persist key in `localStorage` with explicit consent and warning message.
- The field MUST be a password-type input (masked).
- A **"Test API Key"** button MUST verify the key before proceeding.

### FR-02 Language & RTL Support

**Priority:** Must Have  
**Epic:** Epic 1 — Onboarding

#### FR-02.1 — UI Language
- All UI labels, placeholders, buttons, and messages MUST be available in Hebrew and Arabic.
- Language switching MUST not require a page reload.

#### FR-02.2 — Document Language
- Document body text is generated by Gemini in the target language (Hebrew or Arabic).
- Chapter headings follow the official MoE naming conventions in the target language.
- All auto-generated content (table headers, diagram labels) MUST be in the target language.

#### FR-02.3 — RTL Layout
- The UI MUST render correctly in RTL mode for both Hebrew and Arabic.
- Tailwind CSS logical properties (`ms-*`, `me-*`, `ps-*`, `pe-*`) MUST be used — no physical `left`/`right`.
- Icons and chevrons MUST flip appropriately in RTL.
- Number sequences (page numbers, IDs, code line numbers) retain LTR directionality within RTL text.

### FR-03 Database Schema Ingestion

**Priority:** Must Have  
**Epic:** Epic 2 — Resource Extraction

#### FR-03.1 — MS Access Support
- The user MUST be able to upload a `.mdb` or `.accdb` file.
- The system MUST extract:
  - Table names
  - Column names, data types, and sizes
  - Primary key designations
  - Basic foreign key relationships (where available in schema)
- **Implementation note:** Use `mdb-parser` WASM library or equivalent browser-compatible solution.
- If parsing fails, a **manual table entry fallback** MUST be available.

#### FR-03.2 — SQL Server / T-SQL Script Support
- The user MUST be able to upload `.sql` files (T-SQL `CREATE TABLE` scripts).
- The parser MUST extract:
  - Table names
  - Column names, data types, nullability, default values
  - `PRIMARY KEY` constraints and columns
  - `FOREIGN KEY` constraints with referenced table and column
  - `CHECK` constraints (for documentation purposes)
  - `UNIQUE` constraints
  - Index definitions (for documentation purposes)
- The parser MUST handle:
  - Multi-statement T-SQL files
  - Inline and block comments (strip before parsing)
  - Square-bracket and double-quote quoted identifiers
  - `GO` batch separators

#### FR-03.3 — Schema Review & Correction
- After extraction, the system MUST display:
  - A structured table view of all extracted tables and columns
  - PK/FK relationships highlighted
- The user MUST be able to:
  - Edit any field name, type, or description
  - Mark/unmark a field as PK or FK
  - Add missing fields manually
  - Delete false-positive fields
  - Add a human-readable description per table and per field

#### FR-03.4 — Manual Entry Fallback
- If no file is uploaded, the user MUST be able to define tables and fields manually through a form UI.
- The manual entry UI MUST support the same data model as FR-03.1/FR-03.2.

### FR-04 C# Source Code Upload & Parsing

**Priority:** Must Have  
**Epic:** Epic 2 — Resource Extraction

#### FR-04.1 — Folder/File Upload
- The user MUST be able to upload a folder of C# source files using the browser's directory picker (`<input type="file" webkitdirectory>`).
- The system MUST filter for `.cs` files only.
- Maximum total upload size: 50 MB.

#### FR-04.2 — C# Class Extraction
The parser MUST extract from each `.cs` file:

| Element | Detail |
|---------|--------|
| Namespace | Fully qualified |
| Class / Interface / Enum name | Including access modifier |
| Base class / interfaces implemented | For inheritance diagram |
| Properties | Name, type, access modifier |
| Methods | Name, return type, parameter list, access modifier |
| Constructor signatures | Overloads |
| Fields | Name, type, access modifier |
| XML doc-comments (`///`) | Summary, param, returns |
| Attributes | `[HttpGet]`, `[Authorize]`, etc. |

#### FR-04.3 — Class Filtering
- The user MUST be able to:
  - Exclude auto-generated files (e.g., `*.Designer.cs`, `*.g.cs`)
  - Exclude test files (e.g., files in `/Tests/` folders)
  - Mark individual classes as "exclude from documentation"
- The system SHOULD auto-exclude: nested `Program.cs` boilerplate, `Migrations/` folders.

#### FR-04.4 — Code Snippet Selection
- The user MUST be able to mark individual methods or properties as "key code for Implementation chapter"
- Selected snippets will be included as formatted code blocks in the docx Implementation chapter.
- A maximum of **20 key snippets** can be selected (to prevent chapter bloat).

### FR-06 AI Content Generation (Gemini)

**Priority:** Must Have  
**Epic:** Epic 3 — Document Content Editing

All Gemini API calls MUST:
- Use the free gemini model.
- Include a system prompt instructing the model to respond in the configured output language.
- Handle rate-limit errors gracefully with retry-with-backoff.
- Display a loading/progress indicator during generation.
- Never block the UI — use async/non-blocking patterns.

#### FR-06.1 — Introduction Chapter Generation
Input: School metadata, project type, project name, goals (from onboarding)  
Output: Full Introduction chapter text including:
- Project description (2–3 paragraphs)
- Target audience description
- Problem/motivation statement
- System goals (primary + secondary)
- Development environment description
- Key challenges and innovations identified from class structure

Gemini prompt strategy:
- Send class listing + DB table names as context
- Ask for formal, academic Hebrew/Arabic technical writing

#### FR-06.2 — System Analysis Narrative
Input: UseCase participants + DB ERD data  
Output: Written description of workflows and system boundaries for the System Analysis chapter.

#### FR-06.3 — Database Description
Input: Extracted table + column metadata  
Output per table:
- Table purpose description (1–2 sentences)
- Field-by-field explanation
- Normalization justification (why is this table in its current form)

#### FR-06.4 — Class Logic Summarization
Input: Class name + properties + method signatures + XML doc comments  
Output per class:
- One-paragraph responsibility description
- Key methods explained (what they do, why they matter)
- Design pattern used (if recognizable)

Constraint: Only class structure is sent to Gemini — **not full method bodies** — to minimize data exposure.

#### FR-06.5 — AI Usage Documentation
**Mandatory MoE section:** A section documenting all AI-generated content in the project.  
Output: Auto-generated section listing:
- Sections/classes where AI (Gemini) was used in the project itself
- The prompts/contexts used
- How the student validated the output

This section is auto-filled but the student MUST review it.

#### FR-06.6 — Reflection Seed
Input: Project metadata, challenges noted by student  
Output: A structured reflection scaffold (bullet points/outline) that the student fills in — NOT fully auto-written, per MoE expectation of genuine personal reflection.

### FR-07 Visual Diagram Generation

**Priority:** Must Have  
**Epic:** Epic 3 — Document Content Editing

#### FR-07.1 — UML Class Diagram
- Input: Parsed C# class hierarchy data
- Output: **Mermaid.js `classDiagram`** definition string
- Must include:
  - Inheritance relationships (`--|>`)
  - Composition / association (`o--`, `*--`)
  - Interface implementation (`..>`)
  - Key properties and method signatures per class
- Rendering: Mermaid preview shown in UI before export
- Export: Diagram is rendered to SVG/PNG for embedding in docx

#### FR-07.2 — ERD (Entity-Relationship Diagram)
- Input: Extracted table + PK/FK data
- Output: **Mermaid.js `erDiagram`** definition string
- Must include:
  - All tables with their columns and types
  - PK and FK markers
  - Relationship lines with cardinality (1-to-many, many-to-many)
- Rendering: Mermaid preview shown in UI before export
- Export: Rendered to SVG/PNG for embedding in docx

#### FR-07.3 — DFD Level-0
- Input: System name, main input/output flows (manually specified or AI-inferred)
- Output: Mermaid `flowchart` diagram representing system boundary and main data flows
- The student MUST be able to edit the diagram definition before export

#### FR-07.4 — UseCase Diagram
- Input: User types (from onboarding) + key workflows (auto-detected or manually entered)
- Output: Mermaid diagram representing actors and their use cases
- The student MUST be able to add/remove use cases manually

#### FR-07.5 — Diagram Export
- All diagrams MUST be exportable as PNG images sized appropriately for A4 Word page width
- Diagrams embedded in docx MUST preserve aspect ratio
- Diagrams MUST also be available for manual download as PNG

### FR-08 Document Chapter Composition

**Priority:** Must Have  
**Epic:** Epic 4 — Final Generation

The document generator assembles all data into a `.docx` file using `docx.js`.

#### FR-08.1 — Cover Page
- Word: School logo (if uploaded), all metadata fields, formatted as an official cover page
- Font: David MT 14pt for title, 12pt for details
- Borders/decoration: Standard professional layout

#### FR-08.2 — Table of Contents
- Auto-generated Word TOC field
- Based on Heading 1 (chapters) and Heading 2 (sections)
- Updates when document is opened in Word

#### FR-08.3 — Chapter 1: Introduction
- AI-generated text (FR-06.1)
- Student-editable before generation

#### FR-08.4 — Chapter 2: System Analysis
- Narrative text (FR-06.2)
- UseCase diagram image
- DFD-0 diagram image
- ERD overview image
- Process tree image (if provided)

#### FR-08.5 — Chapter 3: Database
- ERD diagram (detailed version)
- Per-table section: table name, description, formatted column table (field | type | PK/FK | description)
- Normalization discussion (AI-generated, FR-06.3)

#### FR-08.6 — Chapter 4 & 5: Implementation (Server + Client Side)
- UML Class diagram
- Per-class section: class name, description (FR-06.4), selected code snippets
- Security section: SQL injection protection, encryption notes (FR-06.4)
- Async/await usage explanation
- Network services layer description
- Business logic layer description

#### FR-08.7 — Chapter 6: User Guide
- Per-user-type section header
- For each workflow: text instructions + screenshot in sequence
- Screenshot captions as figure labels

#### FR-08.8 — Chapter 7: Reflection & Bibliography
- Reflection scaffold (student-filled — cannot be AI-generated per MoE guidelines)
- Bibliography in APA format (manually entered entries + student-filled)

#### FR-08.9 — Chapter 8: Appendices
- Code documentation for all classes (formatted, syntax-highlighted where possible)
- Technology notes (auto-populated from project type selection)

#### FR-08.10 — Formatting
All chapters MUST use:
- Font: **David MT** (Hebrew/Arabic), size 12pt
- Paragraph direction: RTL (`bidi: true`)
- Line spacing: 1.5
- Margins: 2.5cm all sides (standard A4)
- Header: Student name + page number
- Footer: Project name + school name
- Heading 1: Bold, 14pt, centered
- Heading 2: Bold, 12pt
- Code blocks: Courier New, 10pt, LTR, with border

## 3. Non-Functional Requirements

### NFR-01 — Performance
| Metric | Target |
|--------|--------|
| Initial page load (cold) | < 3 seconds on 10 Mbps connection |
| C# code parsing (50 files) | < 5 seconds |
| T-SQL parsing (10k lines) | < 2 seconds |
| Gemini API call (per section) | Display streaming output; complete in < 30 seconds |
| Document assembly (all chapters) | < 10 seconds after all sections approved |
| Mermaid diagram rendering | < 3 seconds per diagram |

### NFR-02 — Browser Compatibility
- **Primary:** Chrome 120+, Edge 120+
- **Secondary:** Firefox 115+, Safari 17+
- File API (directory picker): Requires Chrome/Edge (document this limitation)

### NFR-03 — Accessibility
- WCAG 2.1 Level AA
- All interactive elements keyboard-navigable
- Screen reader support for form fields and status messages
- Color contrast ratio ≥ 4.5:1

### NFR-04 — Usability
- Students with no developer background complete the full workflow in < 30 minutes
- All error messages are descriptive and actionable (in Hebrew/Arabic)
- Tooltip help text on all complex fields

### NFR-05 — Reliability
- 80% of document content successfully auto-generated without manual intervention
- Partial generation: if one chapter fails, remaining chapters still generate
- Session state survives browser tab refresh (via `sessionStorage`)

### NFR-06 — Privacy & Security
- No network requests except to Gemini API (using user's own key)
- No analytics / tracking libraries
- Content Security Policy: `default-src 'self'`; `connect-src api.google.com`

### NFR-07 — Maintainability
- TypeScript coverage: 100% (no `any`)
- Cyclomatic complexity per function: ≤ 10
- Each chapter builder is a standalone module replaceable without affecting others
- MoE chapter requirements stored in a config object (not hardcoded), allowing updates without code changes

## 6. UI/UX Requirements

### 6.1 — Wizard Flow
The application MUST follow a linear wizard/stepper pattern:

```
Step 1: Welcome & Language   →
Step 2: School Details       →
Step 3: Project Type         →
Step 4: API Key              →
Step 5: Database Upload      →
Step 6: Code Upload          →
Step 7: Screenshots          →
Step 8: AI Generation        →
Step 9: Review & Edit        →
Step 10: Export
```

Back navigation MUST be allowed at any step without losing data.

### 6.2 — Progress Indicator
- Persistent step indicator at the top (or side for RTL) showing completed/active/upcoming steps
- Each step shows an icon, short label, and completion status

### 6.3 — Responsive Design
- Desktop first (1280px+): Two-column layout (sidebar + main content)
- Tablet (768px+): Single column, compact wizard
- Mobile: Not a priority for v1.0 (acknowledge limitation)

### 6.4 — Loading & Error States
- Skeleton loaders for AI generation events
- Inline error messages (not modal dialogs) for form validation
- Toast notifications for async successes/failures (upload complete, generation done)
- Global error boundary with "Retry" option

### 6.5 — Review UI
- Side-by-side layout: AI-generated text (left/right in RTL) + editable version
- Accept/Reject toggle for each paragraph
- "Regenerate section" button with optional custom prompt input

## 7. Constraints

1. **No backend infrastructure** — All processing in browser. No Node.js server, no serverless functions.
2. **Student's own Gemini API key** — The tool does not include a shared API key.
3. **MS Access file parsing** — Browser-based MDB parsing has limited support; manual fallback is always available.
4. **50 MB code upload limit** — Enforced to keep in-memory processing feasible.
5. **Gemini context window** — Class documentation is chunked to stay within token limits; very large codebases (>200 files) are processed in batches with progress indication.
6. **No automated tests runners** — The tool generates documentation; it does not execute student code.
7. **MoE rubric version** — Current implementation targets questionnaire **883589** (2024–2026 version). Rubric changes require config updates.
